Registries

The registries are the core's extension points. Functions and providers live in name-keyed maps; sync handlers and field discoverers live in maps keyed by (function, provider). Scope resolution — the rule the product is built around — also lives here.

Role
Hold registered definitions and answer lookups without letting callers mutate them.
Called by
bootstrap() writes; the sync engine, connect flows, mapping editor and capability layer read.
Calls
object-schema.ts for function object ownership.
Key entry
resolveScopes(), requireSyncHandler(), providerRegistry

Key files

FileResponsibility
registry.ts Generic Registry<T>: name validation, duplicate rejection and defensive copying on read and write.
function-registry.ts registerFunction(), resolveScopes(), missingScopes(), scopesAreCovered() and the function/provider lookup helpers.
provider-registry.ts registerProvider() validation, requireOAuth(), canRefresh(), credential resolution and tenant-scope helpers.
handler-registry.ts Sync handler and field discovery registration, keyed function:provider; rejects objects the function does not own.
types/registry.ts FunctionDefinition, ProviderDefinition, ProviderAuth, SyncHandler, FieldDiscovery.

How it fits

  • The generic registry guards its map. It validates names, rejects duplicates, and lets each registry supply a clone-on-read function; function definitions are cloned on the way in and out, while provider definitions are served as registered. A failed registration leaves every existing entry untouched.
  • Functions carry their own scope map. FunctionDefinition.scopesByProvider is the mechanism behind “purposes first, permissions second”: each function declares what each provider would need.
  • resolveScopes() unions the selected set. Given several functions and one provider, it returns the union of their declared scopes and nothing else. It throws when a function is unregistered or declares no scopes for that provider.
  • Granted scopes are compared, not assumed. missingScopes() and scopesAreCovered() let a reconnect prompt surface a genuine gap instead of a mid-sync 403.
  • Providers have two credential shapes. ProviderAuth is a discriminated union: OAuth authorization-code and static API key. Registration validates the hooks each shape requires.
  • Tenant scoping is validated. A provider whose external ids are tenant-scoped must supply a tenantScopeValue hook; externalIdScope must be global or tenant.
  • Handlers are keyed by function and provider. registerSyncHandler() also checks that every declared object is one the function owns, so a catalog handler cannot claim customers.
  • Discovery is registered the same way. A field discoverer is optional; a provider without one yields an empty list and the mapping editor falls back to free-text entry.

Rules worth knowing

  • Bootstrap before lookup. A registry read before bootstrap() sees an empty map. That applies to cross-reference validation too, because it consults the provider registry.
  • Registration failures are loud and early. Missing auth, a tenant-scoped provider without a scope hook, a handler with no objects or a handler claiming a foreign object all throw at startup rather than at sync time.
  • Scopes belong to a pair, not a provider. Holding them per (function, provider) is what lets HubSpot's request widen when Support is added while Salesforce's api scope stays the same.
  • Do not mutate a returned provider definition. Provider entries are served as registered; function entries are cloned. Either way, treat what you get back as read-only.

Open this when…

  • The connect flow requests the wrong permissions.
  • You need to know why a function/provider pair is offered or filtered out.
  • A reconnect prompt says the granted scopes no longer cover the selection.
  • You are registering a new provider and need the required auth hooks.
  • A handler or discoverer is not found at sync or mapping time.
