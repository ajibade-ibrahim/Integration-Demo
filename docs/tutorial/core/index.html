Core

src/core is the working engine: it decides what a connection may do, fetches data from providers, translates it, writes records, and matches companies across connections. The screens in src/app call into it; it never calls back.

It has no next/* imports and no imports from src/app. The same code therefore runs from a route handler, a script or a test with no HTTP server involved.

Location
src/core/
Entry seam
bootstrap() in bootstrap.ts — every entry point calls it first
Framework rule
No Next.js imports; persistence reaches the shared Prisma client in src/lib

How the pieces fit

A connection moves through four stages. Each stage has one owning subsystem, which is the page to open when that part misbehaves.

  • 1. Connect Connection lifecycle
  • 2. Map Field mapping
  • 3. Sync Sync + Providers
  • 4. Resolve Identity resolution

Subsystems

Subsystem What it owns Open first
Registration & capability The one place functions, providers and handlers are declared, and the stricter check that decides what may actually be connected. bootstrap.ts, capabilities.ts
Object schemas Every target a mapping rule may write to, plus the function/object ownership and write order the sync depends on. object-schema.ts
Registries Name-keyed lookup for functions and providers, and (function, provider)-keyed lookup for sync handlers and field discoverers. registries/function-registry.ts
Field mapping Validation, application and serialization of translation rules, including transforms and the content hash that explains an older run. field-mapper/field-mapper.ts
Sync Refresh orchestration, parent-first writes, relinking, leases, coverage, scheduling and field discovery. sync/sync-engine.ts
Providers The provider contract, the shared HTTP failure policy and one folder per outside system. providers/http.ts
Identity resolution Matching customer records across connections onto one company profile, with evidence, survivorship, provenance and human verdicts. identity/identity-resolver.ts
Connection lifecycle Drafts, OAuth, API keys, credential storage, mapping seeding and deletion. integrations/draft-store.ts
Repositories Grouped data-access modules for connections, mappings, runs, synced records, identity and the account read model. repositories/

Cross-cutting rules

  • Purposes decide permissions. A function declares its scopes per provider, and resolveScopes() returns the union for the selected set. See Registries.
  • Target paths are object-qualified. A rule writes to customer.domain, never a bare domain, so a contact field cannot land on a company. See Object schemas.
  • Order is load-bearing. Functions run identity → catalog → agreement → billing, and each function writes parents before children. See Object schemas and Sync.
  • One bad record never aborts a refresh. Failures are recorded per record with a reason, and the run reports partial. See Sync.
  • Provider code holds no orchestration. A provider folder knows how to authenticate, page and interpret its own API; the engine decides when to call it. See Providers.
  • Persistence is concentrated, not exclusive. Most reads and writes go through repositories/, but a few modules import the Prisma client directly where a transaction spans many rows or a lease must be fenced. See Repositories.
