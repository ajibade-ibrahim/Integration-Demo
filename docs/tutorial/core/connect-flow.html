Deep dive

Connect flow

Both credential kinds take the same shape: configure a draft, prove a credential, then create the integration. OAuth proves it with a consent screen and a code exchange; an API key proves it with a probe. Everything after that proof — the row, the encrypted credential, the authorized status, the default mappings — is shared.

The shared shape

  • 1. Draft Provider + functions, no row
  • 2. Prove Consent or key probe
  • 3. Create Row + encrypted credential
  • 4. Finalize Authorized + seeded mappings

The draft is the design decision that makes failed attempts cheap. A draft is a row in its own table, not an Integration: provider, functions, label and an expiry. It survives a rejected credential so the user can retry without re-picking, and it is consumed only after a real integration exists.

File: src/core/integrations/draft-store.ts, created by POST /api/integrations.

OAuth: draft to authorized

1. Build the authorization request

The start route accepts a draftId for a first connect or an integrationId for a reconnect. It checks that the URL's provider segment matches the stored record, then calls buildAuthorizationRequest():

  • resolveScopes() unions the scopes of every selected function for that provider. Adding a function later widens the requirement, which is why checkReauthorization() exists.
  • issueState() creates a single-use, expiring state token whose subject is either the draft or the existing integration.
  • The provider's own buildAuthorizeParams() hook supplies the quirks, and the browser is redirected to the consent screen.

Files: src/app/api/oauth/[provider]/start/route.ts, src/core/oauth/oauth-service.ts, src/core/oauth/state-store.ts.

2. Handle the callback

The callback route calls handleCallback(). State is validated and consumed before the authorization code is used, so a mismatched or replayed state discards the code unexchanged.

  • First connect. The draft branch checks the provider and capability again, exchanges the code, and calls createIntegrationFromDraft(). The draft is discarded only after the integration and credential are written.
  • Reconnect. The existing row is updated, not recreated. A provider denial or failed exchange sets error and keeps the row, its mappings and its synced records. Deleting would lose data that a reconnect is supposed to preserve.
  • Granted scopes. The provider's response is recorded when it names scopes. Otherwise the requested scopes are used. Recording the grant rather than the request is what makes a later coverage check meaningful.

File: src/core/oauth/oauth-service.ts.

API key: paste, probe, create

An API-key provider has no authorization server, so the draft connect URL points to /integrations/new/connect?draft=… instead. The submit route is POST /api/integrations/connect, body-only and no-store: a key in a query string would land in logs, history and the Referer header.

connectDraftWithApiKey() performs three checks in order:

  1. Local shape. validateKeyShape() rejects an empty value or whitespace before any network call. It deliberately does not guess a provider's key format; a false rejection is worse than a round trip.
  2. A real probe. probeCredential() makes the cheapest authenticated request the provider offers. A 401/403 must throw InvalidApiKeyError; anything else is an ordinary failure and is reported as retryable.
  3. Create and finalize. Only a proven key reaches createIntegrationFromDraft(). The draft stays intact on a rejected key, so the user can paste again.

The stored token has no expiry: NON_EXPIRING_AT plus metadata.authKind = "apiKey" keeps it off the refresh path. The metadata also keeps a non-secret prefix and last four characters so a user can recognise which key is connected.

Files: src/core/credentials/api-key-service.ts, src/core/providers/<provider>/provider.ts, src/app/api/integrations/connect/route.ts.

The shared finish

finalizeConnection() is the only post-credential path:

  1. Refuses any function/provider pair without a handler. This is the last guard before a connection can exist but never sync.
  2. Records the source account. For a global provider the scope value is deliberately empty; for a tenant-scoped provider it must name the account, or no self-key is emitted.
  3. Marks the integration active.
  4. Seeds default mappings with seedMappingsIfEmpty() — only when the function has no saved rules.

File: src/core/integrations/connection.ts.

Why defaults matter

A connection with no rules would authorize successfully and then write nothing. Seeding is what makes “connected” mean “able to sync now”. It is also why reconnecting is safe: seeding never overwrites a user's edits.

Credential storage and refresh

  • Encryption. Credentials are encrypted with AES-256-GCM and stored as v1.<iv>.<tag>.<ciphertext>. Every write uses a fresh IV, and a tampered payload fails to decrypt rather than returning garbage.
  • No fallback key. TOKEN_ENCRYPTION_KEY must be present and decode to 32 bytes. A key committed to the code is not protection.
  • Proactive refresh. getValidToken() refreshes five minutes before expiry. A provider that omits a new refresh token on refresh keeps the stored one.
  • Mid-run refresh. OAuth handlers receive refreshAccessToken so a 401 on page 40 costs one request, not the whole run. API-key handlers do not: a 401 there is terminal and becomes a reconnect prompt.
  • Coverage. checkReauthorization() compares the stored grant with the scopes the current function set needs, and names the uncovered functions so the UI can say “reconnect to add Support”.

Files: src/core/oauth/crypto.ts, src/core/oauth/oauth-service.ts, src/core/repositories/token-repository.ts.

Reconnect and re-key

Reconnecting is intentionally different from connecting for the first time. The integration may already hold edited mappings, synced records and resolved accounts, so the failure policy flips:

  • OAuth reconnect failure sets the status to error. Nothing is deleted.
  • API-key re-key rejection sets error and keeps the row. A transient probe failure changes nothing, because it is not evidence about the key.
  • API-key re-key success saves the new credential, records the source account, and re-runs finalizeConnection().

File: src/core/credentials/api-key-service.ts.

SituationWhat happensWhat survives
Draft expiresRefused with “start it again” (410 on the OAuth start route)Nothing — there was never an integration

Unsupported function/providerRefused before the draft or at finalizeNothing connected

Checkpoints

  • npx vitest run tests/unit/oauth-crypto.test.ts — encryption, state single-use and expiry, with no database.
  • npx vitest run tests/integration/draft-connect.test.ts — accepted and rejected keys, draft preservation, replay prevention and re-keying. Needs TEST_DATABASE_URL.
  • npx vitest run tests/unit/provider-auth-kinds.test.ts — the registration rules for both credential shapes.
  • Walk the Mock CRM flow in the browser; every redirect and the final ?connected=1 landing are the OAuth branch above.
  • Inspect Integration, IntegrationDraft, OAuthToken and FieldMapping rows in Prisma Studio before and after a failed attempt.

The invariant. If the credential is not proven, there is nothing to delete. Every failure path is designed to preserve that.
