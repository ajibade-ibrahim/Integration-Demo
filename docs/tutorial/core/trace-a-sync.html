Trace a sync

One complete identity sync through the built-in Mock CRM. It needs no external credentials, so every step is observable: the draft, the consent screen, the token exchange, the refresh, the writers, and the identity pass that turns the resulting rows into company profiles.

Before you start

The Mock CRM is opt-in. It registers only when ENABLE_MOCK_PROVIDER is "true", and its authorize, token and revoke endpoints are routes inside this app. Add these values to .env before starting the dev server:

ENABLE_MOCK_PROVIDER="true"
MOCK_CLIENT_ID="mock-client-id"
MOCK_CLIENT_SECRET="mock-client-secret"
APP_BASE_URL="http://localhost:3000"

# base64 of 32 random bytes — generate one with the command below
TOKEN_ENCRYPTION_KEY="..."
DATABASE_URL="postgresql://..."

Generate a key, build the schema, seed the demo user, and start the app:

node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
npm install
npm run db:push
npm run seed
npm run dev

The demo sign-in. The seed creates demo@integration-demo.local. Its password is printed once, or is whatever you put in DEMO_USER_PASSWORD. The mock client id and secret can be any non-empty strings; the mock token endpoint does not check them.

1. Draft the connection

The New integration page posts the pair the user chose. No Integration row is created yet:

POST /api/integrations
{ "providerName": "mock", "functionNames": ["identity"] }

createDraft() in integrations/draft-store.ts stores the choice in an expiring row — 30 minutes — and returns a connectUrl. The response carries a draft, not an integration, because an abandoned attempt must leave nothing to clean up.

File to open: src/app/api/integrations/route.ts. It calls bootstrap() first, rejects unknown functions, then asks unsupportedFunctionsFor() whether this provider can actually sync Identity.

2. Consent shows exactly the identity scopes

draftConnectHrefFor("mock", draftId) sends the browser to /api/oauth/mock/start?draftId=…. That route:

  • loads the draft and insists the URL's provider segment matches it;
  • calls buildAuthorizationRequest(), which runs resolveScopes(["identity"], "mock");
  • issues a single-use OAuth state token keyed to the draft;
  • redirects to the mock's own authorize route with client_id, redirect_uri, the unioned scopes and state.

Identity on Mock declares three scopes: companies read, contacts read, and schema read. The mock consent screen renders exactly that list. Approving it sends code and state to /api/oauth/mock/callback.

Files: src/app/api/oauth/[provider]/start/route.ts, src/core/oauth/oauth-service.ts, src/app/api/oauth/mock/authorize/route.ts.

3. The callback creates the row and stores the credential

handleCallback() validates and consumes the state before touching the code. It then exchanges the code at the mock token endpoint, which returns a 15-minute access token, a refresh token, and an echoed scope list.

Tracing a first-time connect:

  1. completeDraftCallback() re-checks that the pair is syncable and resolves the requested scopes.
  2. createIntegrationFromDraft() creates the Integration row, stores the encrypted token, and calls finalizeConnection().
  3. finalizeConnection() records the source account, marks the row active, and seeds mockIdentityDefaults.
  4. The draft and state are discarded. The browser lands on the integration page with ?connected=1.

The seeded rules are the reason a fresh connection can sync immediately. They map company name, website → domain, industry, creation date, lifecycle stage and one custom field; for contacts they map first name, email, job title and phone.

Files: src/core/oauth/oauth-service.ts, src/core/integrations/connection.ts, src/core/providers/mock/defaults.ts.

4. Sync starts

Sync now posts to /api/integrations/{id}/sync. The route checks ownership, status active and the capability set, then calls executeSync(id, { trigger: "manual" }). Add ?wait=1 to run inline; scripts and tests use that form.

The engine takes the in-process guard, acquires the durable lease and its SyncRun, then snapshots the mapping rules before the first provider request. The snapshot's content hash is recorded on the run, so a mapping edit during this refresh cannot change half of it.

File: src/core/sync/sync-engine.ts, then src/core/sync/lease.ts.

5. The handler yields companies, then contacts

mockIdentityHandler paginates the fixtures three records at a time. It yields every customer page first, then every contact page, because the writer resolves a contact's company from the index built by the customer pass.

There are 11 companies and 23 people. The awkward records are deliberate:

  • p-018 has a malformed email;
  • p-019 points at a company that does not exist;
  • p-020 has no company at all.

File: src/core/providers/mock/identity-handler.ts and fixtures.ts.

6. The mapper applies the seeded rules

applyMappings() walks the snapshot for each record. The rule set is function-scoped: a contact rule cannot write a customer field. A missing source path produces null, not a dropped key, so every mapped record has a stable shape.

requestedSourcePaths() groups the mapped provider paths by target object. The mock ignores the map — its fixture universe is small — but the real handlers use it to skip whole provider passes.

File: src/core/field-mapper/field-mapper.ts.

7. Writers persist parents before children

writeRecordsForFunction("identity", …) calls writeCustomers(), then writeContacts() with the customer index.

  • Customers upsert on (integrationId, externalSourceId). A malformed customer email is warned about and nulled, because a company's identity is its name and external id.
  • Contacts require a name and reject a malformed email — the record is refused, and the run continues. A missing company link is kept with a warning, and the provider id is retained for a later relink.
  • Relinking runs after the writes, so a child stranded by an earlier run can find a parent that has now arrived.

File: src/core/sync/record-writer.ts.

8. The run closes with counts and coverage

Any rejected record makes the run partial; the writes that succeeded are kept. The close writes record counts, per-record issues, coverage and the mapping versions, and only advances lastSyncTimestamp when the lease is still held.

Expect 11 customers and 22 contacts: p-018 was rejected. The run is partial for the same reason.

9. Identity resolution groups the result

The sync route calls resolveAfterSync(userId, "sync") unless the run was discarded. That pass is per owner, not per integration. It retires keys from deleted connections, reaps empty accounts, loads every customer in a canonical order, builds evidence, places each record, then recomputes each account's fields.

With one Mock CRM connection, each company still has a distinct self-key, so the expected result is 11 accounts. Contacts do not merge companies; they contribute email evidence to the company they are linked to. The convergent fixtures (c-009 through c-011) only join when a Stripe or Metrifox connection supplies the matching email or domain.

Files: src/core/identity/resolve-after-sync.ts, src/core/identity/identity-resolver.ts.

Checkpoints

  • Open the integration's mapping page before syncing: the seeded rules should already be filled in.
  • Open the run history: the rejected issue should name p-018 and the email field.
  • Open Customers: 11 accounts, with contacts attached to their companies.
  • Run npm run db:studio and compare the SyncRun, Customer, Contact and CustomerAccount tables.
  • Sync again: counts repeat because upserts count as writes, but no rows are duplicated and no accounts are recreated.

Why the run is not success. A rejected record is data the user needs to know about, even when every other record wrote cleanly. partial is the honest status, not a failure of the sync.
