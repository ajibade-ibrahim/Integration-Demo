Object schemas

object-schema.ts is the composed registry of every internal record a mapping rule may target. It also records which function owns each object and the order those objects must be written in — facts the validator, the mapping UI, the sync engine and identity resolution all read from the same place.

Role
One source of truth for target fields, object ownership and write order.
Called by
Mapping validation, the mapping editor, record validation and survivorship.
Calls
providerRegistry to validate crossRef.<provider> paths.
Key entry
OBJECT_SCHEMAS, objectsForFunction(), functionsInWriteOrder()

Key files

FileResponsibility
object-schema.ts Composes the per-object schemas; defines FieldDefinition, FUNCTION_OBJECTS, FUNCTION_WRITE_ORDER, custom-field limits and resolveTargetField().
identity-schema.ts customer and contact fields, plus the objects that accept a crossRef.<provider> path.
catalog-schema.ts product, offering, price, feature and entitlement.
agreement-schema.ts agreement, subscription, agreementItem, agreementEntitlement and agreementDiscount.
billing-schema.ts invoice, invoiceLine and payment.
price-format.ts Money and recurrence formatting shared by the pages and read models.

How it fits

  • A field definition is a contract. Each FieldDefinition carries a name, human label, kind (string, email, date, enum, number, boolean), and optional required, maxLength, enumValues, readOnly and conflictPolicy.
  • Targets are object-qualified. A rule writes to customer.domain, not domain. A flat namespace would let contact.email validate against a customer record.
  • Read-only fields are excluded from the editor. associatedCustomerId and associatedProductId are derived from the provider's own foreign id by the sync engine, so mapping a provider id into them would write our internal UUIDs into the wrong slot.
  • Extras have a bounded shape. customFields.<key> accepts 1–100 alphanumeric/underscore characters, with at most 50 custom fields per record and a 1000-character value limit.
  • Cross-references are checked against the registry. crossRef.<provider> is valid only on a CROSS_REF_OBJECTS target and only when that provider is registered — which means bootstrap() must have run.
  • Ownership is separate from the object list. FUNCTION_OBJECTS says which function may write which object; FUNCTION_WRITE_ORDER says the order functions must run in.
  • Inside a function, parents come first. Identity writes customer then contact; catalog writes product → offering → price → feature → entitlement; agreement and billing follow the same rule. The engine reads this order instead of hardcoding a sequence.
  • Conflict policy is per field. The default is highestPriority: the highest-ranked connection supplying a non-null value wins. createDate uses earliest, because an earlier sighting is evidence the company existed earlier.

Rules worth knowing

  • Four consumers, one definition. Validation, the target dropdown, sync record validation and survivorship read the same schemas, so they cannot drift.
  • Adding an object is a multi-file change. A new target needs a schema entry, membership in FUNCTION_OBJECTS, the handler's declared objects and a writer branch. Missing any one of them produces either a refused mapping or a sync that silently writes nothing.
  • Function names are literals here on purpose. bootstrap.ts imports every provider, and providers reach the schema, so importing the constants back would close a cycle. Unit tests pin the registered functions against this map.
  • Unknown functions still have an order. functionsInWriteOrder() sorts unknown names last and preserves their relative order; a function with no objects cannot be anyone's parent.

Open this when…

  • The mapping editor does not offer a target field you expected.
  • A mapping validates but writes nothing.
  • You are adding a field, an object or a whole function.
  • A parent link is null after the first sync.
  • You need to know which function owns a particular table.
