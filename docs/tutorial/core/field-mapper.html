Field mapping

A translation rule says: take this provider field, optionally clean it up, and store it as that field of ours. The mapper validates those rules, applies them to one raw record, and gives each rule set a content version so an older sync run stays explainable after an edit.

Role
Validate rule sets, apply them to provider records, and version the mapping.
Called by
The mapping editor and save route; executeSync() during every refresh.
Calls
object-schema.ts for valid targets; transforms.ts for clean-up.
Key entry
validateMappings(), applyMappings(), mappingVersionFor()

Key files

FileResponsibility
field-mapper.ts validateMappings, readPath, applyMappings, requestedSourcePaths, serializeMappings, deserializeMappings.
transforms.ts none, trim, lowercase, domainFromUrl and dateOnly. Exports the host-extraction helper identity resolution also uses.
mapping-version.ts mappingVersionFor() and MAPPING_RULE_VERSION — the v1-<sha256> identity of a rule set.
types/mapping.ts FieldMappingRule, FieldMappingConfig, MappedRecord, violations and serialized shapes.

How it fits

  • Validation is function-scoped. validateMappings(functionName, rules) checks every rule and reports every violation at once. A rule targeting an object the function does not write is refused rather than saved and silently ignored.
  • Targets resolve through the schema. Built-in fields, customFields.<key> and crossRef.<provider> are all resolved by resolveTargetField(), so the mapper never keeps a second list.
  • Application reads one raw record. applyMappings() walks each rule, reads the provider path, applies the transform and writes the target. A rule whose source is absent yields a blank value, not a missing field, so records keep a stable shape.
  • Absent sources are visible to providers. requestedSourcePaths() tells a handler which provider fields the current rules actually ask for. Handlers use it to skip whole passes — for example, Stripe's catalog handler does not fan out per-product feature requests when no feature field is mapped.
  • Transforms format; they do not interpret. Trim, lowercase, extract a domain, keep a date. Mapping one provider vocabulary onto another belongs in a handler, where an unknown value can have an explicit policy instead of a hidden guess.
  • Versions are content-addressed. The version is computed from the rules themselves, not row ids or insertion order, so reordering rules does not create a new version. MAPPING_RULE_VERSION is folded in and bumped when a deploy changes what a rule means.
  • The run records the version before fetching. The snapshot is written to the sync run before the first provider request and never recomputed, so editing the mapping during a refresh affects the next run, not the one already paging.

Rules worth knowing

  • Object qualification is the safety property. Without it, a contact rule could validate against a customer record and write the wrong shape.
  • Defaults are seeded, never enforced. A connection can sync immediately because defaults are pre-filled, but seedMappingsIfEmpty refuses to overwrite rules a user saved.
  • Two transforms must not diverge. domainFromUrl is exported because identity resolution needs the same host extraction. A second implementation would silently fail to join records rather than error.
  • Serialization is explicit. Rules are stored as a serialized config with a schema version; deserializeMappings() is the matching read path.

Open this when…

  • A mapping save is refused and you need the exact violation.
  • A synced value is blank or has the wrong shape.
  • A provider pass is skipped because no rule asked for its fields.
  • You need to explain which rules an older run used.
  • You are adding a transform and need to know whether it belongs here or in a handler.
