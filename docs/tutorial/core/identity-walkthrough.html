Identity walkthrough

Three systems describe the same company. Resolution turns them into three customer rows, keeps those rows untouched, and produces one combined account. This walkthrough uses the exact fixture behind tests/integration/identity-resolution.test.ts, so every intermediate key and final count is assertable.

Entry
resolveIdentities(userId, trigger)
Scope
One owner — all their connections at once
Triggered by
After sync, manually, or after a deletion or withdrawal
Invariants
Total, idempotent, order-independent
Regression test
tests/integration/identity-resolution.test.ts

The input

One tenant has three connections and four customers. Priorities are all different, so every field has an unambiguous winner and the run raises no issues.

ConnectionPriorityRecordValues supplied
Stripe 10 cus_1 — Acme Name Acme Corp, email billing@acme.example, created 2023-04-01
HubSpot (portal-1) 50 12345 — Acme Name Acme Manufacturing Inc, domain acme.example, industry Manufacturing, type customer, created 2019-01-15
HubSpot contact 50 hs-c-1 Billing@Acme.example — mixed case on purpose
Metrifox (acct-9) 100 m-1 — Acme Name Acme, email billing@acme.example
Stripe 10 cus_2 — Northwind ap@northwind.example — must stay separate

Step 1: load and scope

loadResolutionInput() returns every customer in a canonical order: priority, provider name, instance label, then record id. That chain ends in a unique column, so input order cannot decide the result.

buildForeignScopes() decides which provider ids a cross-reference may safely name. A provider qualifies only when every connection of that provider resolves to the same scope value:

  • Stripe is global, so its scope segment is empty.
  • HubSpot is tenant; metadata carries hubId: "portal-1".
  • Metrifox is tenant; metadata carries accountId: "acct-9".

Two HubSpot portals, or two Metrifox accounts, would make that provider's foreign references ambiguous and drop them. A self-key is unaffected: it knows exactly which connection it came from.

Step 2: build evidence

buildEvidence() is pure and fail-closed. A key it cannot build correctly is not built at all, because a wrong key merges companies while a missing key only costs a join.

KindSourceWhy
external_refSelf id, plus mapped and imported cross-referencesStrongest; a hard id is not a guess
emailCustomer email, legacy custom fields, linked contact emailsUniversal; every provider maps a contact email
domainThe mapped domain column onlyWeakest; never harvested from an email host

Emails are trimmed and lowercased, and plus-tags are stripped. Dots are preserved, because collapsing them is Gmail-specific and would merge two different people at other providers. Free mailbox hosts are classified as freemail: they may still be an email key, but they never become a domain key.

This fixture indexes exactly seven keys:

domain:acme.example
email:ap@northwind.example
email:billing@acme.example
external_ref:hubspot:portal-1:12345
external_ref:metrifox:acct-9:m-1
external_ref:stripe::cus_1
external_ref:stripe::cus_2

There is one email:billing@acme.example though three records supplied it: Stripe's own field, the HubSpot contact (after normalization) and Metrifox. The first occurrence keeps the strongest source label; the other two collapse into it.

Step 3: cluster and place

Clustering applies human same assertions before any key is looked up. A same group pools its evidence and is placed as one unit, not member by member. Without that, whichever member happened to be processed first would choose the home for the group, and the result would depend on row order.

Each cluster then reads fresh matches from the database:

  1. Find accounts by key. Any existing account holding one of the cluster's keys is a candidate.
  2. Apply distinct vetoes. An account the user has ruled out is dropped, and the shared key is reported as blocked_by_assertion — once per customer/account pair, not once per key.
  3. Drop self-key tautologies. A record's own id says “this record is itself”; it is evidence for other records naming that id, never a reason to move this one.
  4. Choose a winner. Strongest key kind, then oldest account, then smallest id. The chain ends in a unique column, so it cannot tie.
  5. Create, attach or absorb. A cluster with no candidates creates an account from its first member. Otherwise the member moves to the winner; a singleton account it already held is absorbed, carrying its keys over. Populated accounts are never merged.

In this fixture the Acme Stripe record (priority 10) is processed before HubSpot (50) and Metrifox (100), so it creates the Acme account and indexes its self-key and email. HubSpot then matches that account on the contact's normalized email and joins. Metrifox matches on the same email and joins. Northwind's email matches nothing and gets its own account. The two Stripe records have equal priority, so their relative order comes from the unique id and has no effect: they share no key.

File: src/core/identity/identity-resolver.ts, plus assertions.ts and evidence.ts.

Step 4: survivorship

After placement, recomputeAccountFields() rebuilds every account from its final membership. The rule that matters most: a null is not an opinion. Each field is contested only among the members that actually supply it.

  • Name and email go to Stripe (priority 10): Acme Corp and billing@acme.example.
  • Industry, domain and type go to HubSpot (priority 50), because Stripe supplies none of them. A whole-row implementation would have blanked all three the moment Stripe was ranked first.
  • Creation date goes to HubSpot's 2019 value under the earliest policy. Stripe saw the company in 2023, but it demonstrably existed in 2019; rank would produce a date known to be wrong.
  • Empty strings count as no value, so a blank from a high-ranked source cannot beat a real value from a lower one.

Survivorship never decides membership. It receives the members it is told about and returns values; changing a priority changes what an account reports, never who is in it.

File: src/core/identity/survivorship.ts.

Step 5: provenance

Each winning field carries a source-evidence entry: integration, provider, instance label, customer id, external id, evidence key and value, and observation time. Losers are retained in alternatives with the reason they lost — even when the priorities are unequal and no conflict issue is raised.

When two members at equal priority supply different values, the run raises field_conflict. The value is still deterministic, but the issue tells the user that the tiebreak was alphabetical rather than meaningful. earliest fields raise no conflict: there is nothing to prefer when the rule is “the oldest one”.

File: src/core/identity/provenance.ts reads both the current provenance shape and the older bare-integration-id shape.

What can go wrong

  • key_claimed_elsewhere — two accounts hold one address and only a human can settle it. The pass picks a home and does not re-parent anyone else.
  • blocked_by_assertion — a shared key was vetoed by a distinct verdict. The report names the key and the customer it would have joined.
  • field_conflict — two equally ranked sources disagree on a field. The value is chosen deterministically; the issue says the preference was not actually expressed.
  • key_race_lost — a concurrent pass inserted the key between the lookup and the write. It resolves itself next pass and is not shown to the user.
  • discarded — a pass was already running for this owner. No run row is written; the owning pass will finish the work.

Checkpoints

  • npx vitest run tests/unit/identity-evidence.test.ts — the key emission table above, including the mixed-case normalization.
  • npx vitest run tests/unit/identity-survivorship.test.ts — null never wins, per-field composition, earliest date and provenance alternatives.
  • npx vitest run tests/unit/identity-assertions.test.ts — same grouping and distinct vetoes.
  • npx vitest run tests/integration/identity-resolution.test.ts — the exact three-connection fixture and the two final groupings. Needs TEST_DATABASE_URL.

The asymmetry to remember. A missed merge costs one same assertion. A false merge has no user-facing undo. Every ambiguous decision in the resolver therefore errs toward leaving records apart.
