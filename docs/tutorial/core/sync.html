Sync

A refresh is one pass: fetch, translate, save and report. sync-engine.ts owns the invariants that hold for every provider — one run at a time, functions in write order, parents before children, per-record failures that never abort the run, and a durable account of what happened.

Role
Orchestrate a refresh, write mapped records, and record status and coverage.
Called by
The manual sync route and runScheduledSyncs().
Calls
A provider handler, applyMappings(), the record writers, resolveAfterSync().
Key entry
executeSync()

How it fits

  • The engine starts with a fast guard. An in-process Set stops the common double-click; the database lease is the cross-instance authority.
  • A fresh credential comes first. getValidToken() and refreshToken() renew OAuth credentials before paging; an API key does not expire.
  • Functions run in a fixed order. functionsInWriteOrder() sorts identity → catalog → agreement → billing. Later functions reference earlier ones, so this is what lets one refresh fully connect everything.
  • The handler fetches; the mapper translates; the writer saves. The engine resolves the handler for (function, provider), hands it a session, then applies the function's rules to each yielded record.
  • Parents are written before children. Each writer builds an external→internal index and children resolve through it, falling back to a database lookup for parents written by an earlier run.
  • Relinking repairs earlier gaps. A child kept with a null link is found again after later records arrive, so an agreement can link its customer and offering without a second full sync.
  • Status describes writes, coverage describes acquisition. A run can be success with unverified coverage. The run row carries both plus the mapping version each function used.
  • Scheduling is a plain function. isDue() decides which active integrations are due; runScheduledSyncs() runs them and then triggers identity resolution for each affected owner.

Rules worth knowing

  • Per-record failure never aborts the run. A rejected record is reported with a reason and severity; the rest are written and the run finishes partial. A run that found another live run is discarded, not failed.
  • An unresolved child is usually kept. It is written with a null link and a warning, retaining the provider id so a later run links it. The exceptions are an agreementItem, an agreementEntitlement, an agreementDiscount and an invoiceLine, whose parent arrived in the same payload and whose foreign key is required.
  • Only four lists are reconciled. Agreement lines, agreement entitlements, agreement discounts and invoice lines can have entries removed. Two gates protect that: the list must be mapped, and the provider must have declared it complete — a page-capped list looks exactly like a shorter one.
  • Everything else is update-only. A record that stops arriving stays until the connection is deleted. That is the known gap behind a removed catalog feature lingering.
  • The lease is fenced. Closing checks the owner, token and expiry under the lock, so a paused old worker cannot overwrite a newer run or advance lastSyncTimestamp after losing ownership.
  • Resolution failure never fails the sync. resolveAfterSync() logs and swallows it; the resolver is idempotent, so the next pass covers the same rows.

Open this when…

  • A run reports partial and you need the per-record reason.
  • A child record has a null parent link.
  • Two syncs were requested at once and one was discarded.
  • A worker crashed and the run is stuck or abandoned.
  • A scheduled integration is not running when expected.
  • The field dropdown in the mapping editor is empty or stale.
