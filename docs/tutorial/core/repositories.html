Repositories

Most of the core's database access is grouped here by subject. Repositories keep Prisma queries and owner scoping out of the orchestration code, and give the identity pass a single audited place where the userId filter has to be present.

Role
Grouped reads and writes for connections, credentials, mappings, runs, synced records and identity.
Called by
Sync, connection lifecycle, identity resolution, mapping editor and the pages.
Calls
src/lib/prisma.ts and json-column.ts helpers.
Key entry
The repository matching the subject you are changing

Inventory

GroupFilesWhat it owns
Connections & credentials integration-repository.ts, token-repository.ts, user-repository.ts Integration rows and status, schedules, source account; encrypted tokens and non-expiring keys; the single owner account.
Mappings & discovery mapping-repository.ts, discovered-field-repository.ts Saved rules per function, seeding defaults, retargeting; the cached field list used by the mapping editor.
Sync runs sync-run-repository.ts Run history, status, record counts, issues, coverage and mapping-version snapshots.
Synced records synced-data-repository.ts, catalog-repository.ts, agreement-repository.ts, billing-repository.ts Read models and queries for customers/contacts, catalog, agreements and billing.
Identity identity-repository.ts, identity-withdrawal-repository.ts Customers, accounts, evidence keys, assertions and resolution runs; deletion and withdrawal tombstones.
Account read model account-commercial-repository.ts The commercial view across an account's member records: agreement counts, next renewal, invoice and payment state.
Helpers json-column.ts Typed read/write helpers for JSON array, object, count and scope-list columns.

How it fits

  • Owner scoping is enforced in query conditions. Connections, records, combined profiles and mappings belong to one owner; every read and write carries that owner in its where clause.
  • Identity has one guarded module. identity-repository.ts is the only repository that touches the identity tables, and the only place the userId filter has to be audited.
  • Repositories are grouped by subject, not by table. A single file can cover a read model plus its related child queries, which keeps a page or a pass from stitching together several repositories.
  • JSON columns go through helpers. json-column.ts centralizes the parse/serialize rules for arrays, objects, counts and scope lists, so a malformed column is handled the same way everywhere.
  • Some writes intentionally bypass repositories. sync/record-writer.ts uses the Prisma client directly for its batched, parent-first writes; sync/lease.ts for the transaction that fences a run; oauth/state-store.ts and integrations/draft-store.ts for their short-lived rows; and identity/source-account.ts when recording a tenant scope.
  • Transactions are where the invariant is. Mapping saves and deletions replace or remove related rows inside one transaction, so a partial save cannot leave a rule set or an account in an impossible state.

Rules worth knowing

  • Do not repeat the “repositories are the only Prisma importer” claim. It is not true in the current code; the direct importers are listed above and are deliberate.
  • Owner conditions are not optional. A repository function without an owner filter is a cross-tenant bug, not a shortcut.
  • Read models are shaped for their callers. The account commercial repository returns a page ready for the account view; it does not expose raw tables for the page to join.
  • Identity tables have one door. Adding a query against them elsewhere duplicates the owner audit and is the mistake the split exists to prevent.

Open this when…

  • You need to know where a table is read or written.
  • A page shows another owner's data or misses rows for the current owner.
  • A transaction leaves a partial mapping or a half-deleted integration.
  • You are adding a read model and need the right grouping.
  • A JSON column fails to parse or loses a value.
