Registration & capability

bootstrap.ts is the one place where functions, providers and handlers are declared. capabilities.ts asks the stricter question the picker, connect API and integration page need: given a declared pair, can this provider actually sync this function today?

Role
Populate the registries, then filter declarations down to real capabilities.
Called by
Every entry point — routes, scripts and tests — before reading a registry.
Calls
registerProvider, registerFunction, registerSyncHandler, registerFieldDiscovery.
Key entry
bootstrap(), canSyncFunction()

Key files

FileResponsibility
bootstrap.ts All registrations, in one idempotent function. Also exports the function-name constants and resetBootstrapForTests().
capabilities.ts supportedObjectsFor(), canSyncFunction() and unsupportedFunctionsFor() — the connectable set.
types/registry.ts The definitions being registered: FunctionDefinition, ProviderDefinition, SyncHandler, FieldDiscovery and the credential union.
registries/* The maps that hold the definitions. Details in Registries.

How it fits

  • One call, once. A module-level guard makes bootstrap() safe to call from every entry point. Calling it twice is a no-op, not a duplicate-registration error.
  • Providers first. HubSpot, Salesforce, Metrifox, Stripe, Chargebee and Stigg register unconditionally. The Mock CRM registers only when isMockEnabled() says the deployment opted in.
  • Functions declare scopes. Each FunctionDefinition carries a scopesByProvider map. Identity, Catalog, Agreement and Billing have real entries; Support keeps declarations for the roadmap; Usage and Communication are registered with an empty map.
  • Handlers are the narrower claim. A function can be declared for a provider without having a handler. registerSyncHandler() records the implementation and its target objects, and rejects objects the function does not own.
  • Capability requires all three facts. canSyncFunction() returns true only when a handler exists, it declares at least one object, the provider is registered, and scope resolution succeeds for the pair.
  • The UI and the API agree. unsupportedFunctionsFor() is what filters the picker and what finalizeConnection() checks before creating a connection.

Rules worth knowing

  • Declaration is not implementation. Scope declarations keep consent and the roadmap honest; capability keeps an unbuilt pair out of the connect flow. That is why “no system supports this yet” is a real state rather than a connection that authorizes and then writes nothing.
  • Registration is all-or-nothing per definition. Validation runs before anything is written, so a rejected definition leaves the registry untouched. Duplicate names throw.
  • Handler objects are checked at registration. A handler that claims an object its function does not write fails immediately, rather than validating cleanly and silently writing nothing.
  • Bootstrap order is not a dependency graph. The function does not require providers to be registered before handlers; the checks that need both happen later, at connect and mapping time.

Open this when…

  • You are adding a provider and need to know which registrations to add.
  • A provider or function is missing from the New integration picker.
  • The consent screen asks for the wrong scopes.
  • You see “already registered” or “claims objects the function does not write”.
  • A function is selectable but a sync finds no handler.
